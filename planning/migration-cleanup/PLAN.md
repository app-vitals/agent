# Plan: migration-cleanup — drop one-off Saul-migration tooling, fix the consumer-compat guard

Session: `migration-cleanup` · Primary repo: `app-vitals/agent` (MCL-2.1 targets `app-vitals/shipwright`) · Prefix: `MCL`

## Design summary

The Saul lane move (session `saul-lane-move`) left two kinds of residue, and the guard that should protect shipwright from
this repo's changes turned out to block additive work.

1. **One-off tooling on the specialty-change branch.** PR #127 carries the specialty `PATCH` (SAL-1.2, kept) plus SAL-1.3's
   dry-run preview route, a `previewSystemCrons` service method and a `classifySystemCrons` refactor of
   `reconcileSystemCrons`: about 1,100 lines for a one-agent, one-time flip. The preview adds a method to the cron service
   that breaks shipwright's typed test fakes. Reconcile needs no change at all; the one real hazard (Saul's enabled
   `learn-dream` cron) was handled by converting that row to a user cron by hand (SAL-1.1).
2. **The shipwright bake in the specialists image** (vitals-os #7332) is replaced by DB-driven remote marketplaces (session
   `public-marketplaces`). Its removal is handled there (PMK-2.1), widened to a true revert.
3. **`shipwright consumer compat`** (required check) fails for reasons that are not breaking changes:
   - `migration-guard` runs shipwright's `additiveViolations()`, which rejects the foreign key Prisma emits for any new
     related table (`ALTER TABLE ... ADD CONSTRAINT ... FOREIGN KEY ... ON DELETE CASCADE`: not on the allowlist, and `ON
     DELETE` trips the destructive-keyword regex). This blocks PMK-1.1.
   - `admin-gen drift` regenerates shipwright's committed admin spec/types and asserts no diff. Those files are only
     regenerated by shipwright's own bump workflow after publish, so any PR that changes the admin surface deadlocks.
     It also lets a removed API field slip past the typecheck, which runs on the stale committed types first.

### The guard stays read-only toward shipwright
`consumer-compat.yml` runs on `pull_request` only, with `contents: read`, no secrets and `persist-credentials: false`, in a
throwaway checkout (tests already assert this). The only thing that writes to shipwright is shipwright's own
`platform-release.yml` bump, which regenerates the committed admin spec/types, `docs/platform`, `bun.lock` and
`agent/Dockerfile` and aborts on any other changed file. This plan does not change that; MCL-2.2 adds a test that the
guard itself never pushes, opens a PR or uses a credential.

### What still fails after the fix
Removing or renaming something shipwright uses still fails: the typecheck runs on shipwright's real code (production and
tests) against the PR's packed packages, after the admin spec/types are regenerated, so a removed response field fails
where shipwright reads it. `migration-guard` still rejects DROP, DELETE, UPDATE, TRUNCATE, RENAME, NOT NULL without
DEFAULT and constraints on existing tables. Not covered, and never was: runtime behaviour changes with no type change,
untyped access (raw SQL, hand-written fetches, env vars), and shipwright's e2e, chart and image checks.

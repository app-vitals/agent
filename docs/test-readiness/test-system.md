# Test System Design

> Phase 2 of the test-readiness pipeline. The greenfield blueprint for the ideal test system that would satisfy the Phase 1 inventory. Does NOT account for existing tests — that's Phase 3.
>
> Generated by `/test-design` on `2026-11-26` (blueprint unchanged from 2026-11-20; the CI split into gates / unit / integration / smoke jobs with an aggregate `ci` check, per-layer bunfig files and the `shipwright-coverage` artifact upload landed since 2026-11-25 and match this target shape; the new inventory items — GitHub repo cache (`github-repo-cache`, `github-sync-cached-access`, `github-access-backfill`: integration against real Postgres), the GitHub crawlers/refresher (integration with recorded fixtures, e.g. `admin/src/fixtures/github-agent-installation-cassette.json`), `platform-routes` (smoke) and the small pure helpers (unit) — are covered by the existing matrix and local-substitute rules).
>
> Everything below is a **target state**, not a claim about what exists today. The only current-state facts used are CI job names and the workspace layout, taken from `.github/workflows/ci.yml` and `package.json`; verify against the working tree before scoping work.

## Stack profile (from inventory)

TypeScript on Bun (workspaces `lib`, `runtime`, `admin`, `chat`); Prisma + Postgres in admin and chat; Kubernetes client in the admin provisioner; GitHub, Slack, Anthropic identity, Google/Okta and web-push integrations; Playwright for admin UI journeys. `deploy_model` is undeclared, so canary eligibility is skipped for this repo (see the canary section).

## Framework matrix per layer

| Layer | Framework | Rationale |
|---|---|---|
| Unit | `bun test` | Matrix default for TypeScript on Bun; fast, built-in coverage with an lcov reporter. |
| Integration | `bun test` + real Postgres (CI service container, local via mise-provisioned `pg_ctl`; testcontainers where Docker is available) | Prisma-backed services must hit a real DB through the service interface; never mock at the ORM level. |
| Smoke | `bun test` driving the Hono app in-process (`app.request`) | Wire contract only (status, shape, auth); no browser needed. |
| E2E | Playwright (`admin/e2e/`) | Admin UI journeys need a real browser; the matrix default. |

## Local execution architecture

Every external dependency from the inventory, with its local substitute. No test in this system may require a hosted external service.

| Dependency | Local substitute | Setup file |
|---|---|---|
| Postgres (admin, chat) | Real DB per run: one Postgres instance, separate databases per service (`agent_admin_test`, `shipwright_chat_test`), `prisma migrate deploy` before the layer | `scripts/test-db-setup.sh` (to create); CI uses the existing service container |
| Kubernetes API (provisioner, `kubernetes-client.ts`) | Typed client interface with an in-memory fake; wire-level behaviour via hand-authored JSON fixtures | `admin/src/test-support/kubernetes-fake.ts` (to create) |
| GitHub REST / App / Enterprise APIs | Recorded fixtures (hand-authored JSON via `Bun.serve` stub or msw); mock the client interface for unit tests | `lib/test-support/fixtures/github/` (to create) |
| Slack Web API / Socket Mode (runtime, admin provisioning) | Recorded fixtures plus a local WebSocket stub for socket events | `runtime/test-support/fixtures/slack/` (to create) |
| Anthropic identity / federation, Google, Okta | Recorded fixtures; JWKS served from a local stub with generated keys | `admin/src/test-support/idp-stub.ts` (to create) |
| Chat service (runtime ↔ chat, admin ↔ chat) | The real chat app in-process on an ephemeral port against the test DB, or a client-interface fake for unit tests | `chat/src/test-fakes.ts` (reuse the concept) |
| Web push endpoints | Local HTTP listener capturing payloads; fixed VAPID test keys | `admin/src/test-support/push-sink.ts` (to create) |
| `claude` CLI subprocess | Scripted fake binary on `PATH` replaying stream-json fixtures | `runtime/test-support/fake-claude/` (to create) |
| `git` / `gh` CLI, filesystem | Real `git` against temp-dir repos; `gh` replaced by a PATH stub | `runtime/test-support/tmp-repo.ts` (to create) |
| TTS/STT (piper) | Capture-only stub binary | `runtime/test-support/fake-piper` (to create) |

**Blockers (no clean local substitute):**

- None blocking. Two caveats: (1) a full Kubernetes behaviour check (RBAC, admission) has no local substitute short of kind/k3d; the design covers client contract and manifest shape only, and real-cluster behaviour stays a deploy-time concern. (2) Recorded fixtures for third-party APIs need a re-recording loop, which `repo-config` marks deferred.

## Canary execution contract

Same code, separate entry point:

- **Canary entry point:** `bun run test:canary` (to create; runs `*.canary.test.ts`, already excluded from default `bun test` by `bunfig.toml`) — never reuses `test:smoke`
- **Unset `TEST_TARGET_URL`** → local mode. Boot dependencies inline, hit `localhost`.
- **Set `TEST_TARGET_URL`** → canary mode. Skip boot, hit the URL, use canary-only auth.

**Eligibility:** layer ∈ {smoke, E2E} AND criticality ∈ {critical, high} AND read-only OR self-cleaning AND zero DB-dependent setup.

**Status for this repo:** `deploy_model` is undeclared in `CLAUDE.md`, so the Phase 1 roster is empty and no canary job is wired. Declare `## Deploy model` to enable it. The first canary candidates would be read-only `GET /health` (runtime) and an unauthenticated admin/chat liveness route.

**Budget:** <60s wall time for the full canary suite.

**Gate:** canary failure blocks promotion (staging → prod or equivalent).

**CI jobs:**
- `smoke` — pre-merge, runs `bun run test:smoke`, boots local deps
- `canary` — post-deploy, sets `TEST_TARGET_URL` to the deployed staging URL, runs `bun run test:canary` (not created while `deploy_model` is undeclared)

See `${CLAUDE_PLUGIN_ROOT}/skills/canary-execution/SKILL.md` for the full contract.

## Test-data strategy

- **Per-service DBs vs. shared:** per-service databases on one Postgres instance (`agent_admin_test`, `shipwright_chat_test`); no cross-service table access.
- **Real DB per test run vs. transaction rollback:** one real DB per workspace per run, truncate-between-files (not rollback), because services use their own transactions (`prisma-tx.ts`) and files run in parallel against separate databases.
- **Factories vs. fixtures:** factories (account, agent, template, thread, token) for variable state; fixtures only for stable golden cases (GitHub/Slack payloads, stream-json transcripts).
- **Seed strategy:** named seed sets (`minimal-account`, `account-with-agents`, `enterprise-github`) built through service functions or the public API where it exists; direct DB writes only for state the API cannot express (legacy rows, corrupt-state tests).
- **Eventual consistency:** async paths are sweepers, the chat poller, cron sync, the stall reaper and push sending. Tests assert via an injected clock and explicit "run once" entry points rather than sleeps; where a real wait is unavoidable, poll with 5 retries, 500 ms base, 5 s cap.

## CI pipeline shape

```
lint / typecheck / boundary / deps / config-docs / admin-types-drift   (fast gates)
        │
        ▼
unit-all  (bun test, *.test.ts, no DB)  ──fail──▶ stop
        │
        ▼
integration-all  (bun test *.integration.test.ts, Postgres service)  ──fail──▶ stop
        │
        ▼
smoke-all  (bun test *.smoke.test.ts, in-process apps)
        │
        ├─ (parallel, post-merge) admin e2e (Playwright)
        ├─ packed consumer smoke / consumer compat (existing PR checks)
        └─ canary (post-deploy, only when deploy_model: staged)
```

- **Layer order:** unit → integration → smoke. E2E + canary run post-merge / post-deploy.
- **Fail-fast:** lower-layer failure skips higher layers.
- **Parallelism:** one combined job per layer, not a per-workspace matrix. Matrix sharding only if the combined layer misses its budget, a workspace has documented flake/slowness, or projected savings exceed 2× the per-job overhead. Within a job, test files run concurrently with bun's default workers; DB-backed files use per-worker database names.
- **Budget:** <15 min total per PR.
- **Coverage toolchain:** `lcov` via `bun test --coverage --coverage-reporter=lcov`.
- **Coverage report path:** `coverage/lcov.info`
- **Coverage artifact upload:** on pushes to the default branch, upload `coverage/lcov.info` as the `shipwright-coverage` workflow artifact (`actions/upload-artifact`, `name: shipwright-coverage`).

**Naming convention:** `*.test.ts` or `*.unit.test.ts` = unit; `*.integration.test.ts`; `*.smoke.test.ts`; `*.canary.test.ts` (canary only); `admin/e2e/*.e2e.ts` (Playwright only).

**Runner exclusion config:**
- Default `bun test` (unit): `bunfig.toml` `pathIgnorePatterns` extended with `**/*.integration.test.ts`, `**/*.smoke.test.ts`, `**/*.canary.test.ts`, `**/admin/e2e/**`.
- Integration / smoke scripts select by path glob (`bun test "**/*.integration.test.ts"`).
- Playwright `testMatch: "**/*.e2e.ts"` scoped to `admin/e2e/`.
- Coverage `exclude`: `**/*.fixtures.ts`, `**/test-support/**`, `chat/src/test-fakes.ts`, `lib/admin-types.ts` (generated), `runtime/fixtures/**`.

**Verification:** `bun test --dry-run` (or listing via a small script) must list no `.integration.`, `.smoke.` or `.canary.` files for the unit runner; the mirror check must list only matching files for each other runner.

## Coverage targets

A single floor of ≥80% line and ≥80% branch, enforced by the standard reporter. Criticality only orders the work.

| Tier | Layer | Target |
|---|---|---|
| all | unit | ≥80% line, ≥80% branch (critical-path files aim ≥90% by practice, not a separate gate) |
| critical | integration | every named boundary (Prisma services, Kubernetes client, GitHub/Slack clients, cron/setup/boot) |
| critical | smoke | every public route 200/4xx (admin `*-api.ts`, chat routes, runtime `/health`) |
| critical | E2E | every top-5 journey (sign-in, agent create, agent edit/settings, template apply, agent delete) |
| high | integration | every named boundary |
| high | smoke | happy path |
| medium | smoke | spot-check |

## Speed budgets

| Layer | Per-test 95p | Per-test hard cap | Suite target |
|---|---|---|---|
| Unit | <50 ms | <200 ms | <30 s |
| Integration | <2 s | <10 s | <3 min |
| Smoke | <5 s | <15 s | <30 s seq / <60 s full |
| E2E | <30 s | <90 s | <10 min |
| Full PR pipeline | — | — | **<15 min** |
| Canary suite | — | — | **<60 s** |

Budgets are the defaults; none loosened. Per-test timeouts match the hard caps (`bun test --timeout 200` for unit, 10000 for integration, 15000 for smoke; Playwright `timeout: 90000`). Job `timeout-minutes` = suite target × 1.5 rounded up: unit 1, integration 5, smoke 2, E2E 15.

**Parallelization plan:** the suite must hit target on 2 workers, not just many. Unit and smoke run as one job each on a standard 2-4 vCPU runner using bun's file-level concurrency. Integration runs one job with per-worker databases; no sharding by default. E2E runs as its own job with Playwright `workers: 2`. Revisit sharding only under the Step 6 conditions.

- Test-account / test-agent / thread factories and the named seed sets above.

- IdP/JWKS stub and VAPID test keys.

## Repo configuration

> Without these, the verification commands in each task are advisory. With them, CI is the gate.

### Branch protection (`main`)

- Required status checks: `lint / typecheck / boundary / test` (aggregate job, now fed by separate `gates`, `unit`, `integration` and `smoke` jobs), `admin e2e`, `workflow lint (actionlint / zizmor)`, `packed consumer smoke`, `PR title lint`
- Required PRs (no direct pushes)
- Require branches up-to-date before merging
- Require conversation resolution
- Required approving reviews: 1 (CODEOWNERS)
- Enforce on admins: yes
- Canary status check is NOT required-to-merge (canary is a deploy gate, not a merge gate)

### Required secrets

- No third-party credentials needed for tests (all dependencies are local or fixture-backed).
- `TEST_CANARY_API_KEY` only if `deploy_model` becomes `staged`.
- Fixture re-recording tokens (GitHub, Slack) kept out of CI; used manually in a separate workflow when the recording loop exists.

### Required GitHub Environments

- None required today (`deploy_model` undeclared). If `staged`: `staging` and `production`, with reviewer gates on production.

### PR template

Add `.github/pull_request_template.md` with a Closing Checklist that requires the verification-command output to be pasted in the PR description.
